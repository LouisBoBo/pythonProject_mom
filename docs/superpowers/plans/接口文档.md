## 1. 通用约定

### 1.1 鉴权

控制器继承 `BaseRepository`，带宿主 `[Authorize]`。请求头：

```
Authorization: Bearer {登录 JWT}
Content-Type: application/json
```

令牌由 `POST /api/sys/user/UserLogin` 写在响应头 `Token`。后续请求放在 `Authorization: Bearer {Token}`。未登录或令牌无效时，宿主返回 HTTP 401。除补全接口外，401 会被宿主改写成：

```json
{
  "code": 401,
  "success": false,
  "data": null
}
```

用户编号取 JWT 的 `NameIdentifier`。补全接口还会查 `TBL_SYS_USER`：`CSTATE=D` 视为禁用；查不到该用户不算禁用。

### 1.2 企业

查询不按企业过滤。登录用户可使用全部启用模型，没有按用户再授权。

新增厂商、模型、用量时，`CENTERPRISE_CODE` 取请求头 `Accept` 里的 `enterprisecode$$企业CID`（段之间用 `_-` 分隔）。修改模型或厂商时保留原企业，不改成当前请求的企业。

操作人优先取 `Accept` 里的 `currentusername`，否则取用户表登录名。用量上报人同样取登录名，不信客户端传入的用户。

客户端现状（2026-11-04 核对）：用量上报会解析登录令牌里的 `enterprisecid`，非 0 时自动在 `Accept` 里带上 `enterprisecode$$企业CID`，不需要另配。但三个企业 CID 尚未配置，登录请求不带 `Enterprise`，服务端按 0 处理，令牌里的 `enterprisecid` 也是 0，所以当前上报不带该段，用量行的企业字段为空/0（见 7.6 风险 3）。CID 补齐后登录会带上 `Enterprise`，上报头随之自动生效。

### 1.3 响应外形

除 `POST /api/ai/Chat/Completions` 外，控制器返回 `FunctionResult`，宿主再包一层。客户端实际看到：

```json
{
  "checkType": "N",
  "checkCode": "",
  "severName": "DEFAULT",
  "code": 200,
  "success": true,
  "message": {
    "code": "000000100000000",
    "content": "",
    "msg": "",
    "stackTrace": ""
  },
  "serverDatetime": "2026-11-03 17:19:00.0000000",
  "data": {
    "Success": true,
    "Content": "",
    "code": "0",
    "msg": "",
    "stackTrace": "",
    "Data": null,
    "Datas": {},
    "TotalRows": 0
  }
}
```

业务是否成功看 `data.Success`，业务数据在 `data.Datas`，分页总条数在 `data.TotalRows`。业务失败时 HTTP 仍是 200，外层 `success` 仍为 true，原因在 `data.Content`。下面各接口只写 `data` 里的 `FunctionResult`。

`POST /api/ai/Chat/Completions` 不经过这层包装，也不缓冲响应体。

| 情况                              | 客户端收到的内容                                                |
| --------------------------------- | --------------------------------------------------------------- |
| 业务失败，或非流式成功            | `FunctionResult` 本身，HTTP 200                                 |
| `stream` 为布尔 `true` 且上游 2xx | 上游 SSE 原文，`Content-Type: text/event-stream; charset=utf-8` |

### 1.4 状态与分页

| 值                | 含义         |
| ----------------- | ------------ |
| `CSTATE=A`        | 启用         |
| `CSTATE=D`        | 停用         |
| `CIS_DEFAULT=Y/N` | 是否默认模型 |

分页参数 `pageIndex` 小于 1 时按 1，`pageSize` 小于 1 时按 20，大于 100 时按 100。列表按各接口自己的排序返回当前页。

### 1.5 不回传的字段

厂商 Key `CAPI_KEY` 不出现在任何响应里。维护列表只给 `HasApiKey`。网关日志里的上游失败正文若含 Key，会先替换成 `***` 再截断到 200 字。

## 3. 登录与会话

这三个接口在 `SystemInitController`，前缀 `api/sys`，Swagger 分组 `SYS`。响应同样先是 `FunctionResult`，再由宿主包成第 1.3 节的外层。令牌不在 `Datas` 里，登录成功后从响应头读取。

后续请求带：

```
Authorization: Bearer {响应头 Token}
```

`Authorization` 为空时，可以改带请求头 `Token: {JWT}`。`Authorization` 有值但不是 `Bearer` 时，不再回退 `Token` 头。

### 3.1 登录

> 对接状态：✅ 已完成（2026-11-04 真实服务器验证通过）。桌面端已实现企业编码 + 账号 + 密码登录，密码变换、企业编码携带规则、FunctionResult 解包、响应头 `Token` / `TokenExpires` 读取均按本文档；已在真实服务器用 HB/1 验证登录成功（HTTP 200、返回 `Token` 头、用户何波）。验证码（GetCaptcha）、失败自动重试未接入，风险已确认接受。
>
> 企业 CID 尚未提供，`ENTERPRISE_CIDS` 三个值仍为空，登录请求因此省略 `Enterprise`，服务端按 0 处理。补齐 CID 常量后无需改登录逻辑，`Enterprise` 会随请求发出；用量上报也会从令牌里读到企业 CID 并自动带入 `Accept`。

`POST /api/sys/user/UserLogin`

免登录。每次成功登录新建一个会话，不踢掉其它端已有会话。是否允许多会话由 JWT 配置 `AllowMultiSession` 决定；为 false 时，写入新令牌前会清掉该用户其它会话。

| 字段        | 必填 | 说明                                                                                                                        |
| ----------- | ---- | --------------------------------------------------------------------------------------------------------------------------- |
| UserName    | 是   | 登录账号。服务端去空白并转小写后比对                                                                                        |
| Password    | 是   | 不是明文。先对明文做 UTF-8 MD5，得到 32 位大写十六进制，再取第 9 到第 24 位并转小写，共 16 位。服务端再摘要后与库中密码比较 |
| Enterprise  | 否   | 企业 CID 的十进制字符串，写入 JWT 的 `enterprisecid`。空或非数字时按 0                                                      |
| LoginType   | 否   | `CS` 时 `Datas` 额外带菜单 `Modules` 和精简组织。其它值不返回菜单                                                           |
| CaptchaId   | 条件 | 连续失败次数大于 3 时必填，来自 `GET /api/sys/user/GetCaptcha`                                                              |
| CaptchaCode | 条件 | 与 `CaptchaId` 一起提交，比对忽略大小写                                                                                     |

开启了组织校验（`OrgVerifyEnabled=true`）时，用户必须属于 `Enterprise` 及其下级组织，否则 `Content=当前企业不存在该用户!`。请求里带了网络环境时，用户未关联该网络则 `Content=该用户在当前网络({环境})不允许访问!`。

成功时 HTTP 200，`Success=true`，`TotalRows=1`。`Datas` 是用户对象，`CPASSWORD` 已清空。常用字段：

| 字段          | 说明                                                                |
| ------------- | ------------------------------------------------------------------- |
| CID           | 用户编号，后续接口从 JWT 的 `nameid` 读取同一值                     |
| CUSER_NAME    | 登录账号                                                            |
| CDISPLAY_NAME | 显示名                                                              |
| CIS_ONLINE    | 成功后为 `Y`                                                        |
| Orgs          | 用户组织。`LoginType=CS` 时只含 CID、默认标记、用户、组织编号和名称 |
| Modules       | 仅 `LoginType=CS` 时有菜单及权限                                    |

令牌在响应头，不在 body：

| 响应头                 | 说明                                                 |
| ---------------------- | ---------------------------------------------------- |
| Token                  | Access Token，后续放进 `Authorization: Bearer`       |
| TokenExpires           | Access 过期时间，UTC，`yyyy-MM-ddTHH:mm:ss.fffffffZ` |
| RefRefreshToken        | 刷新令牌。刷新接口不在本节                           |
| RefRefreshTokenExpires | 刷新令牌过期时间，格式同 `TokenExpires`              |

浏览器要能读到这些头，跨域时服务端需把它们列入 `Access-Control-Expose-Headers`。

密码错误、账号停用、用户不存在，对外都是「用户名或密码不正确」。只有密码错误且用户存在时才累加失败次数。验证码错误不计数。已锁定的账号不再累加。

| Content                                                     | Datas                                       | 条件                                                                                     |
| ----------------------------------------------------------- | ------------------------------------------- | ---------------------------------------------------------------------------------------- |
| 用户名或密码不正确!                                         | `{ "NeedCaptcha": false, "Locked": false }` | 失败次数未超过 3                                                                         |
| 用户名或密码不正确，请输入验证码                            | `{ "NeedCaptcha": true, "Locked": false }`  | 失败次数大于 3，且本次没带验证码                                                         |
| 请输入验证码                                                | `NeedCaptcha=true`                          | 已要求验证码但未提交                                                                     |
| 验证码错误                                                  | `NeedCaptcha=true`                          | 验证码不对。用过即失效                                                                   |
| 验证码已过期，请刷新                                        | `NeedCaptcha=true`                          | 超过 5 分钟或已使用                                                                      |
| 验证码服务不可用，请检查 Redis 配置                         | `NeedCaptcha=true`                          | Redis 不可用                                                                             |
| 账号已被锁定，请联系管理员                                  | `{ "NeedCaptcha": false, "Locked": true }`  | 已锁定，或累计失败达到 8 次。管理员把 `CIS_LOCKED_OUT` 改回 `N` 并清零失败次数后才能再登 |
| 当前企业不存在该用户!                                       | 无                                          | 组织校验未通过                                                                           |
| 该用户在当前网络(...)不允许访问!                            | 无                                          | 网络环境不允许                                                                           |
| 403005 系统错误，请联系服务厂商处理！服务电话：400-116-6903 | 无                                          | 并发在线数达到授权上限                                                                   |

连续失败 3 次之内不要求验证码。第 4 次失败后，下一次登录必须先调用 `GET /api/sys/user/GetCaptcha`。该接口免登录，`Datas` 为：

| 字段        | 说明                                                                            |
| ----------- | ------------------------------------------------------------------------------- |
| CaptchaId   | 登录时回传                                                                      |
| ImageBase64 | PNG 的 Base64，不含 `data:image/png;base64,` 前缀。5 分钟内有效，校验一次后删除 |

登录成功会把失败次数清零。

### 3.2 校验 Token

> 对接状态：未对接。客户端启动时不做服务端令牌校验，本机会话文件有效即直接进入；令牌过期后表现为模型请求 401，届时需重新登录。

`GET /api/sys/user/ValidateToken`

需要当前 Access Token。宿主 JWT 签名或过期不通过时，请求到不了本接口，直接是第 1.1 节的 401。本接口在签名有效之后，再按用户和会话核对服务端保存的令牌。

无查询参数，无请求体。

成功：`Success=true`，`Content` 为空，`Datas` 为空。下面两种情况也直接成功，不再比对会话：

- 令牌存储不可用。
- 当前进程没有这条会话记录，且存储不跨进程共享。例如请求落到了没有这份会话的实例。

失败仍是 HTTP 200 的 `FunctionResult`：

| Content             | 条件                                                             |
| ------------------- | ---------------------------------------------------------------- |
| 无效的Token格式     | 请求里读不到 Access Token                                        |
| Token不存在或已过期 | 令牌没有会话号，或服务端已没有这条会话                           |
| Token已失效         | 会话还在，但与当前保存的 Access Token 不一致。例如同一会话已刷新 |

### 3.3 退出

> 对接状态：客户端代码已对接（2026-11-04，待重打包生效），但**服务端该接口当前有缺陷，实测无法成功**。两点实测与本文档不符：① 并非「无请求体」——不带 content-type 返回 415、空 body 返回 400，必须带 `content-type: application/json` 和非空 JSON 体（客户端已按此实现）；② 用有效 Access Token 调用时，服务端返回 `Success=false, Content="Nullable object must have a value"`（服务端空引用异常，与请求体内容无关，换任何字段都一样），需同事修复。客户端「退出登录」逻辑：先尽力调用本接口（5 秒超时、失败只记日志、绝不阻塞），随后照常清除本机凭据与会话；接口修复前等效于仅本地退出。另有限制：令牌只保存在主进程内存中，应用重启后没有可用的令牌，此时退出只会清本机，不会调用服务端；需要先重新登录一次，再退出才能触发服务端注销。

`POST /api/sys/user/UserLogout`

需要当前 Access Token。**注意（2026-11-04 实测修正）：并非无请求体**——不带 content-type 返回 415，body 为空返回 400；必须带 `content-type: application/json` 和非空 JSON 体（`{}` 即可）。只注销这个令牌上的会话，其它端保持登录。

该用户已经没有其它有效会话时，才把 `CIS_ONLINE` 改成 `N`，并释放授权并发占位。仍有其它会话时，不改在线状态。

成功：`Success=true`，`Content` 为空，`Datas` 为空。

失败：`Content=退出失败：请携带当前登录 Token`。令牌里读不出用户编号或会话号时返回这句。签名无效或过期时，同样先被宿主拦成 401。

## 4. 模型

上游地址和厂商 Key 在厂商表。模型只保存别名、显示名、真实模型名、窗口、单价和所属厂商。

### 4.1 可用列表

> 对接状态：✅ 已完成并真实验证通过（2026-11-04）。登录成功后客户端用新令牌调用本接口拉取模型目录，`defaultAlias` 排首位写入缓存（`<userData>/gateway/models.json`），下次启动生成 profile 补丁时优先采用缓存目录、无缓存则回退内置列表；任一环节失败均静默保留内置列表，不影响登录与聊天。真实链路已于 2026-11-04 在同事服务器（对接端口 11231）验证：经本机桥接登录后调用本接口返回 200，目录含 `standard`（DeepSeek-V4.1-Flash，128000/8192）与 `deep`（DeepSeek-V4-Pro，128000/16384），`defaultAlias=standard`。早前在旧端口 6680 上本接口 404（AI 插件未部署），同事切换新端口后插件已启用。

`GET /api/ai/Models/Get`

无查询参数。只返回 `CSTATE=A` 的模型，按 `CSORT`、`CID` 升序。不按企业、不按用户过滤。不返回单价、真实模型名、厂商地址和 Key。

成功 `Datas`：

| 字段                   | 类型   | 说明                                                                   |

## 6. 补全

> 对接状态：✅ 已对接并端到端验证（2026-11-04 15:45）。方案：profile 补丁 baseURL 指向 `{base}/api/ai`（实测路由大小写不敏感），Host 的 openai-completions 模块只支持流式（请求固定 `stream: true`），故非流式包装与数字字符串化缺陷天然绕开。
>
> 验证结果：装机包经 8791 验证桥接到 11231，登录后发「你是谁」得到流式回答（3 秒、20.3K tokens、124 tok/s）；同事在服务端侧 15:40:12 直连同一请求体同样成功（HTTP 200、1.27s、SSE 直到 `[DONE]`，`model` 回报上游真实名 `deepseek-flash`）。11:43–13:37 的「模型服务异常」是服务端厂商链路故障，15:40 前后自行恢复，与客户端传参无关：同一时段 `model=not-a-real-model` 返回「模型不存在或已停用」，说明鉴权、反序列化与别名解析一直正常。
>
> 客户端兜底（2026-11-04 已实现，待重打包）：静态 provider 在发起流式请求时注入 `packages/llm/llm-pi-ai/src/stream-guard.ts`——响应是 2xx 但 `content-type` 不含 `text/event-stream` 时，读取 body 取 `data.Content`（或 OpenAI 的 `error.message`），改写成 400 + 中文纯文本；正文含「限流 / 稍后重试」等字样的记 429。这样业务失败不再被当成断流重试 5 次，用户看到的是服务端原话。空 body 回「模型服务返回了空响应，请稍后重试」；body 实际以 `data:` 开头（只是 content-type 标错）则原样放行。单测 10 项通过。**验证用桥接（8791）不是交付物**，其翻译逻辑与本兜底等价。
>
> 仍待处理：① 服务端若能把失败改成 4xx/5xx + 纯文本 body，这层适配即可去掉；② 装机包尚未包含「baseURL 指向 11231 + 模型列表走 Models/Get + 本兜底」这套改动，需重打包生效。

`POST /api/ai/Chat/Completions`

客户端按 OpenAI Chat Completions 提交 JSON 对象。`model` 填 `GET /api/ai/Models/Get` 返回的 `alias`，不要填真实模型名，也不要填显示名。

网关用别名找到启用模型，把 `model` 换成 `CREAL_MODEL`，用所属厂商的 Key 转发到 `{CBASE_URL}/chat/completions`。不转发用户 JWT。上游超时 5 分钟。

### 6.1 请求体

| 字段                                                      | 网关处理                                                                    |
| --------------------------------------------------------- | --------------------------------------------------------------------------- |
| model                                                     | 必填。必须是已启用模型的别名。转发前换成 `CREAL_MODEL`                      |
| messages                                                  | 原样转发。`content` 可以是字符串、数组或 null                               |
| tools、tool_choice、temperature、top_p 及其它未列出的字段 | 原样转发                                                                    |
| stream                                                    | 必须是 JSON 布尔值。`true` 才走 SSE。字符串 `"true"` 按非流式处理           |
| stream_options                                            | `stream` 为 true 时强制 `include_usage=true`。原来没有该对象会补上          |
| max_completion_tokens                                     | 改名为 `max_tokens` 后转发。若两者同时存在，以 `max_completion_tokens` 为准 |
| store                                                     | 转发前删除                                                                  |

`messages`、`tools`、`tool_choice`、`temperature` 不会被改写。

非流式示例：

```json
{
  "model": "standard",
  "messages": [{ "role": "user", "content": "你好" }],
  "stream": false,
  "max_completion_tokens": 8192,
  "store": false
}
```

流式示例：

```json
{
  "model": "standard",
  "messages": [{ "role": "user", "content": "你好" }],

}
```

### 6.2 转发顺序

1. 令牌里的用户编号能解析成整数，否则「当前登录用户无效」。
2. 用户未被禁用，否则「当前登录用户已被禁用」。
3. 请求体是 JSON 对象，否则「请求体不是合法 JSON」。空 body、数组、字符串都算非法。
4. `model` 去空白后非空，否则「缺少模型别名」。
5. 存在 `CSTATE=A` 且别名相等的模型，否则「模型不存在或已停用」。
6. `CMAX_RPM` 大于 0 时，按「用户 + 别名」做 60 秒滑动窗口。窗口内已达上限则「请求过于频繁，请稍后重试」。计数只在当前进程，多实例不共享。`CMAX_RPM` 小于等于 0 不限流。
7. 厂商 `CSTATE=A` 且根地址非空，否则「模型厂商不存在或已停用」。
8. `CREAL_MODEL` 非空，否则「真实模型名不能为空」。

限流在请求发出前计数。窗口内第 `CMAX_RPM` 次仍然放行，再下一次拒绝。

上游请求头：

| 头              | 值                                      |
| --------------- | --------------------------------------- |
| Authorization   | `Bearer {厂商 Key}`                     |
| Accept          | `text/event-stream, application/json`   |
| Accept-Encoding | `identity`，避免 gzip 把 SSE 压成一整块 |
| x-request-id    | 32 位十六进制，无连字符                 |

### 6.3 非流式响应

`stream` 不是布尔 `true` 时，读完上游正文再返回。HTTP 200，不套宿主外层。

成功时 `Datas` 为上游 JSON。上游 `Content-Type` 含 `event-stream`，或正文不是 JSON 时，`Datas` 为原始字符串。

```json
{
  "Success": true,
  "Content": "",
  "code": "0",
  "msg": "",
  "stackTrace": "",
  "Data": null,
  "Datas": {
    "id": "chatcmpl-demo",
    "object": "chat.completion",
    "model": "deepseek-flash",
    "choices": []
  },
  "TotalRows": 0
}
```

### 6.4 流式响应

`stream` 为布尔 `true` 且上游返回 2xx 时，按块把上游字节写给客户端，不解析、不重组、不包进 `FunctionResult`。

响应头：

| 头                | 值                                 |
| ----------------- | ---------------------------------- |
| Content-Type      | `text/event-stream; charset=utf-8` |
| Cache-Control     | `no-cache, no-transform`           |
| X-Accel-Buffering | `no`                               |
| x-request-id      | 与发给上游的请求号相同             |

正文是上游 SSE，例如：

```
data: {"id":"chatcmpl-1","object":"chat.completion.chunk","choices":[{"index":0,"delta":{"content":"你"}}]}

data: [DONE]
```

读到一块就写出并刷新。流开始之后如果网络中断，连接直接结束，不能再改成 `FunctionResult`。

### 6.5 失败

业务失败都是 HTTP 200 的 `FunctionResult`，`Success=false`，没有 `Datas`。上游非 2xx、超时或连接失败统一为「模型服务异常」，不把上游正文回给客户端。上游状态码和截断正文只进服务端日志。

| Content                  | 条件                                   |
| ------------------------ | -------------------------------------- |
| 当前登录用户无效         | 令牌没有可解析的用户编号               |
| 当前登录用户已被禁用     | 用户 `CSTATE=D`                        |
| 请求体不是合法 JSON      | 空 body、非对象或 JSON 无法解析        |
| 缺少模型别名             | `model` 缺失或空白                     |
| 模型不存在或已停用       | 别名没有启用中的模型                   |
| 请求过于频繁，请稍后重试 | 超过每分钟上限                         |
| 模型厂商不存在或已停用   | 厂商停用、不存在或根地址为空           |
| 真实模型名不能为空       | `CREAL_MODEL` 为空白                   |
| 模型服务异常             | 上游非 2xx，或发出后失败且响应尚未开始 |

`requestId` 已存在时不更新原行，仍然成功。并发插入撞上唯一索引时同样视为重复。

成功：`Datas` 为 `{ "ok": true }`。

| Content                                  | 条件                                 |
| ---------------------------------------- | ------------------------------------ |
| 当前登录用户无效                         | 令牌没有用户编号                     |
| requestId 和 modelAlias 不能为空         | 请求体为空，或两者任一空白           |
| token、费用不能为负，clientTs 必须大于 0 | 数值非法                             |
| latencyMs 不能为负                       | 传了负的耗时                         |
| status 只能是 ok、error 或 aborted       | 状态不在这三项里                     |
| 用量写入失败                             | 插入失败，且库里也没有这条 requestId |

### 7.6 客户端对接评估（2026-11-04）

> 结论基于第 7 节文档与客户端代码核实，未对用量接口做真实调用（令牌在凭据库中，不读取）。

前提：网关不在补全后自动记账，客户端不报就等于服务端没有数据。产品口径为金额不统计，`costYuan` 固定传 `0`（服务端只校验「不能为负」，0 合法）。

| 接口        | 结论           | 理由                                                     |
| ----------- | -------------- | -------------------------------------------------------- |
| Report      | 已实现         | 唯一记账入口；每次模型调用结束上报一条                    |
| Batch       | 不接           | 单条上报已足够，本地补报队列不属于本期范围                |
| My          | 不接           | 本期不做用量面板                                          |
| Summary     | 不接           | 全员汇总，文档未写角色校验，桌面端开放即越权              |
| GetUsageList | 不接          | 同上，且 `keyword` 可按上报人检索，可枚举他人记录         |

数据可得性（已按实际实现核实）：

| 字段         | 来源                                                                 |
| ------------ | -------------------------------------------------------------------- |
| modelAlias   | 本次调用解析到的模型 id，即网关别名                                   |
| inputTokens / outputTokens | 模型流末尾的 `usage` 分块；pi-ai 默认发送 `stream_options.include_usage` |
| status       | finish reason：`stop`/`tool-calls`/`max-tokens` → `ok`，`aborted`、`error` 直映 |
| latencyMs    | 本次调用从发起请求到流结束的毫秒数                                     |
| requestId    | 每次调用 `randomUUID()`，≤36 字符；同一次调用只发一条，不重试、不改写 |

口径与风险：

1. token 口径：客户端 `TokenUsage.inputTokens` 是未缓存输入，缓存命中单列。上报的 `inputTokens` 取 `input + cacheRead + cacheWrite`，否则缓存多时合计偏低。
2. 金额不再可修：`costYuan` 恒 0，`totalCostYuan` 恒 0；服务端同 `requestId` 不更新原行，将来启用计费时历史行无法回填，只能从启用日起算。
3. 企业归属：服务端写用量时取请求头 `Accept` 里的 `enterprisecode$$企业CID`；客户端会从登录令牌的 `enterprisecid` 自动回填这一段。但三个企业 CID 尚未配置，登录不带 `Enterprise`，令牌里是 0，因此当前上报不带该段，企业字段为空/0。若服务端按企业出报表，需先提供三个企业的 CID。
4. 失败调用无 usage：只能报 `status=error` + token 0/0，合计低于真实消耗，但这是数据缺失而非计算错误。
5. 令牌约 6 小时且无刷新：过期后上报返回 401 只记日志；本期没有补报队列，这些调用记录直接丢弃。
6. 越权面：`Summary`、`GetUsageList` 不按企业也不按用户，且文档未写管理员校验；客户端不应提供入口。
7. 误报范围：只有配置了 `usageReportUrl` 的路由才上报；桌面端只为 `zr-gateway` 生成该配置，官方 provider 不会写入公司库。
8. 上报不得影响对话：流结束后异步发送、3 s 超时、失败只打日志不重试；`errorMessage` 由客户端截断到 1000 字并剔除令牌等敏感串。
9. 成功但拿不到 usage：整条丢弃并打日志，不写 0，避免把「未知」记成「零消耗」。

实施方式（已完成，待真机验证）：

- 位置：`llm-pi-ai` 适配器内部，凭据使用本次请求解析到的会话令牌，只放在请求头，不落盘。
- 开关：provider 配置新增可选键 `usageReportUrl`；未配置则完全不发请求，包保持 provider 中立。
- 企业归属：上报时解析令牌载荷里的 `enterprisecid`，非 0 才在 `Accept` 里追加 `enterprisecode$$CID`；令牌不是 JWT 或字段缺失时不加。
- 桌面端：`gatewayPatchBlock` 自动写入 `${baseUrl}/api/ai/Usage/Report`，随登录后的路由补丁一起生成。
- 单测：`usage-report.spec.ts`（21 条，覆盖 token 合计、状态映射、脱敏、字段校验、HTTP/业务失败）与 `usage-report-adapter.spec.ts`（4 条，覆盖成功上报、未配置不发、失败 0/0、令牌不出现在错误文本），桌面端 patch 断言已更新。
- 尚未做的真机验证：需要在真实网关用有效会话发一条对话，确认服务端 `Usage/GetUsageList` 能查到该 `requestId`，并确认企业字段的实际落值（见风险 3）。
